Your camera is the controller.

A gesture is an input event like any other — and the frames it came from never leave the device.

wibbly is an input layer plus a shell that makes camera-controlled games cheap to build, with one reference game (tennis) to prove it. Pose estimation runs in a plain browser tab: no console, no download, no dongle. The input library is real — @vulos/wibbly-input implements all four seams behind 77 unit tests that run without a camera, and the tennis game consumes it. What is still only written down is hand tracking, a second player actually playing, and every form of networked play. This page keeps those two lists apart.

Honest status
React 19 + Vite + Three.js. Phase 1 has landed: the old 480-line detector that injected its own DOM is gone, replaced by @vulos/wibbly-input — MoveNet MultiPose, a spatial player binder, handedness as a sign flip rather than a hardcode, and an adaptive frame pacer, all under passing tests. What those tests prove is the logic, not a room: the multi-person path has unit coverage but has not been validated against real cameras and real people. Tennis still drives one player. Hand tracking, networked play, a desktop shell and a release build do not exist.

An input layer, not a tennis game

Game code never names a model, a runtime or a vendor — it sees four interfaces, and every seam ships a working default. The package exists, the tennis game consumes it, and the recognizers are tested without a camera.

Seam 01

FrameSourceShipped

Where pixels come from. WebcamFrameSource wraps getUserMedia and owns its own capture loop; a native Rust capture path arrives with the desktop shell. The detector no longer appends a preview widget to your <body> — the overlay is a component you place.

Seam 02

PoseTrackerShipped

Pixels to skeletons, returning Person[] — the plural is the entire design decision. MoveNetMultiPoseTracker pins modelType: 'MultiPose.Lightning' and returns up to six skeletons with landmarks normalised to [0,1], which is what unblocked every multi-player capability.

Seam 03

GestureRecognizerShipped

Skeletons to game events. detectSwing is a pure function over landmark history, so 24 of its tests run in CI with no camera, no GPU and nobody waving at a laptop. Handedness is a sign flip — the left-handed TODO is gone.

Seam 04

PlayerBinderShipped

Which skeleton is which player — the hard problem demos skip. SpatialBinder does greedy nearest-centroid matching over torso centroids, with a claim zone per player and a forget timeout for occlusion. It is covered by 18 tests; it has not yet met four real people in a real room.

Grounded choice

Models picked on licenceDecided

MoveNet MultiPose Lightning for bodies, MediaPipe HandLandmarker for hands — both Apache 2.0, both with published in-browser numbers. YOLO-pose is AGPL-3.0, WiLoR is CC BY-NC-ND, HaMeR is research-only. The reasoning is written down so nobody relitigates it.

Grounded choice

Browser-first, deliberatelyDecided

Zero install is the platform's biggest asset: a link, a wave, a game. Tauri comes later as an app shell with capture and inference in Rust — WebKitGTK has no WebGPU, Linux webview cameras are broken by default, and shipping 1080p frames over JSON-serialized IPC costs roughly 250 MB/s.

What's spec'd, not built

Said plainly, so nobody has to reverse-engineer it from the pitch.

  • Multi-person play, proven. The tracker returns six skeletons and the binder assigns stable ids, both under unit test — but neither has been validated against real cameras and real people. Fixtures are not a living room. Treat couch multiplayer as implemented and unproven, which is not the same as working.
  • Two-player tennis. The binder is configured for two claim zones; the game reads gestures for player_1 and ignores the rest. Nobody can currently join by standing in the right half of the frame.
  • Hand tracking. The name says gestures and the code does body pose. MediaPipe HandLandmarker is chosen and licence-cleared; no tracker, no pinch and no point recognizer exists.
  • Decentralized sessions, payments and lobbies. These come from magnetite through an InputProvider seam that has not been added yet. There is no network code in wibbly at all — no client, no transport, no session.
  • A desktop shell. Tauri with Rust-side capture and inference is phase 3. Nothing has been started.
  • A release build. No installer, no Docker image, no hosted deployment. Clone it and run the dev server. Hosting is still configured for Firebase, though the analytics SDK is gone.

Camera frames never leave the device

This is the architectural claim wibbly is built around, and it is worth stating precisely rather than loudly. Inference is local because it has to be — a browser tab has nowhere to send frames that would be fast enough — and the design keeps it local when play goes networked: clients exchange GestureEvents of a few dozen bytes, never video.

Local inference, today

Every frame is captured by getUserMedia, run through MoveNet in the tab, and dropped. No frame is uploaded, stored or proxied. That is true of the code as it exists now, not of a future version.

Events on the wire, later

Networked play is designed, not built. When it lands, each client tracks its own camera and transmits gesture events; hosting, discovery and lobbies come from magnetite. Until then there is no network path at all.

The caveat we won't hide

The build used to initialise Firebase Analytics — central tracking, in a product whose thesis is the opposite. The SDK and its dependency are now gone. Hosting is still Firebase, so the claim holds for your camera and for your page views, but not yet for your DNS lookups.

Quick start

Source-only. Clone it, allow the camera, stand back — there is no release build to install.

git clone https://github.com/vul-os/wibbly
cd wibbly

npm install
npm test            # 77 seam tests, no camera required
npm run dev

# open http://localhost:5173, allow camera access,
# stand ~2 m back and swing. Set handedness in the
# camera preview — it applies on the next frame.
  1. 1
    Clone and installNode 20+, React 19, Vite, Three.js. TensorFlow.js fetches the MoveNet weights on first load and the browser caches them after that.
  2. 2
    Run the seam testsThe recognizers, binder, pacer and calibration are pure logic, so they verify in about two seconds with no camera and no GPU. That is the point of the refactor.
  3. 3
    Stand back and swingAbout two metres, upper body in frame, even lighting. Tennis drives one player today, either handedness. Details in the docs.

Listed alongside the Vulos suite

Vulos is a family of open, self-hostable software. wibbly is fully independent — it runs on a machine you control, needs no Vulos account and no Vulos infrastructure — and shares the suite's posture that computation should happen where the data already is. Its planned platform layer (sessions, discovery, payments) comes from magnetite, which is itself standalone.
